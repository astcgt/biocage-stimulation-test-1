## 0. 物件模型

```
Capability 能力（7 個：5 主要 + 2 次要）
 ├─ question     它要回答的一個問題
 ├─ Facet 面向（2-6 個）── question
 │    └─ Check 檢查（可量測的一項測試）
 │         ├─ method / threshold（門檻與來源：PI 定、已接受、或「提案」）
 │         ├─ configs     適用哪些平台配置
 │         ├─ required    必要（失敗 = 該配置的輸出會錯或不可用）或 診斷（效率、早期警訊；不計入判定）
 │         ├─ depends     依賴哪些元件（元件改了 → 證據過期）
 │         ├─ trigger     何時要跑：每 run／每批／元件變更時／一次性
 │         └─ status[配置] state + date + value + note (+ reconfirmed)
 └─ verdict(配置)  由檢查自動算出

Configuration 平台配置：TIED 黏死篩選（生產）｜FRIC 真實摩擦（驗證）｜GPUFE evo GPU 求解器（L1 快篩）
Component 元件：ANAT MESH BUILD SETTINGS SPLIT FEBIO GPUDIRECT GPUFE OPS PREFLIGHT RETARGET METRICS COLLECT XPLT EQLAW AL
Restriction 使用限制：bounded 界定｜exclusion 禁用｜scope 範圍聲明
```

為什麼要按配置分開判定：同一個能力在不同配置下的合格與否不同。例如 [物理] 的解剖驗證對 TIED 和 FRIC 都成立，
但 gate 4 只是 TIED 的問題，骨元素翻轉只發生在 FRIC。判定永遠寫成「能力 × 配置」，例如「[數值] FRIC 不合格」。

## 1. 判定演算法

**檢查狀態**（登錄在 json）：`pass` 通過｜`fail` 不通過｜`partial` 部分（只覆蓋了部分範圍）｜`not_run` 未做｜`deferred` 暫緩。
程式另外算出 **過期**：檢查依賴的元件在證據日期之後被修改，而且沒有登錄重新確認（`reconfirmed`）。
過期只會讓 pass／partial 降級；fail 保持 fail，但標上「已改動」。

**一條必要檢查對一個配置的判定**：

| 狀態 | 沒有 bounded 限制 | 有 bounded 限制涵蓋 |
|---|---|---|
| pass | 合格 | 合格 |
| fail | **不合格** | 有條件合格 |
| partial／not_run／過期 | **未評** | 有條件合格 |

**面向** = 它的必要檢查中最差的；**能力** = 它的面向中最差的。順序：合格 < 有條件合格 < 未評 < 不合格。
次要能力一律報「暫緩」。診斷檢查只列出，不計入判定。

四個判定的精確意思：
- **合格**：所有必要檢查都有未過期的證據證明通過。
- **有條件合格**：有缺口，但每個缺口都有一條 bounded 限制寫明偏差的方向和上界，結果在這條限制下可以使用。
- **未評**：至少一條必要檢查沒有證據（沒做、只做一部分、證據過期），而且偏差界限不明。不能宣稱合格，也不能宣稱不合格。
- **不合格**：至少一條必要檢查有證據顯示失敗，而且偏差沒有界限。

**使用限制的三種類型**：
- `bounded` 界定：已知偏差的方向和上界（例：R10 取樣過衝 4–13%，方向保守）。只有這一類可以把判定升為「有條件合格」。
- `exclusion` 禁用：結果不得用於某個用途（例：R03 摩擦結果不得用於淘汰）。不升級判定，只規定該怎麼做。
- `scope` 範圍聲明：每份結論都必須附上的一句話（R07 [泛化]、R08 [時程]）。

**覆蓋要明確**：一條檢查通過時，要寫明覆蓋了哪些設計、方向、配置。只覆蓋一部分就登錄成 `partial`，不是 `pass`。
（教訓：10-31 以前的「split = sequential」只比了屈曲，因此漏掉了重啟負荷曲線失效的 bug。）

**證據過期的處理**：重跑該檢查；或確認那次改動不可能影響它，登錄 `reconfirmed {date, note}`。
不准挪動原本的證據日期。

## 2. 七個能力物件

格式：**問題 → 面向（及其問題）→ 由哪些元件實現 → 提供給其他能力什麼 → 需要其他能力提供什麼**。
每個面向的檢查條目、門檻和目前狀態都在計分表的第 5 節。

### 2.1 [物理] 物理真實性（Validation）
- **問題**：模型方程描述的東西，像不像真的人體 C3-C4 加上真的 PLCL cage？（「方程對不對」；「方程解得對不對」屬於 [數值]）
- **面向**：
  - 解剖與節段力學：PHY-01 Herron 對照、PHY-02 FSU 對完整頸椎、PHY-03 軸向撐開剛度
  - cage-骨介面：PHY-05 gate 4；PHY-04 受拉比例（診斷）
  - 材料：PHY-06 材料常數依據
  - 負荷與手術程序：PHY-07 負荷協定；PHY-08 插入與推出（診斷）
- **元件**：ANAT（Herron 2020 26 歲女性 C3-C4，可變形骨、小面關節接觸、韌帶）、BUILD（手術：移除椎間盤、expand 0.8 插入、
  釋放；負荷：100 N 跟隨負荷、1.5 N·m 六向；介面 tied／elastic，mu 0.35）、SETTINGS（PLCL 85:15／50:50，Gent，預應變包裝）。
- **提供**：每個設計、每個方向的力學狀態。
- **需要**：[數值] 確認狀態是方程的正確解；[多元] 給一個可建網格的設計；[觀測] 告訴它要輸出哪些量。

### 2.2 [數值] 數值正確性（Verification）　2026-11-02 新增
- **問題**：方程有沒有被正確地解出來？也就是離散、時間積分、接觸演算法、協定近似和求解器本身的誤差，是否小到不影響判定？
- **為什麼從 [物理] 拆出來**：兩者混在一起時，求解器的假象會被當成物理現象（或反過來）。T02 的偽力矩、T18 的偽滑移、
  骨元素翻轉，都是「方程沒解對」，不是「方程錯了」。
- **面向**：
  - 空間離散：NUM-01 cage 網格收斂（旋轉協定）、NUM-02 端板網格收斂
  - 時間離散與動態近似：NUM-03 時間步收斂、NUM-04 微步偽力矩、NUM-14 剛體動態殘差（重試步偽力矩）
  - 接觸演算法：NUM-05 罰則敏感度、NUM-06 骨元素不翻轉、NUM-13 摩擦錨點重設
  - 協定近似：NUM-07 拆分 vs 連續、NUM-08 慢速動態 vs 靜態；NUM-09 靜態重試混用（診斷）
  - 求解器一致性：NUM-10 補丁回歸、NUM-11 GPU vs CPU、NUM-12 gpufe gate 2–4
- **元件**：FEBIO（4.13 + 本專案補丁）、GPUDIRECT（cuDSS）、GPUFE、SPLIT（拆分視窗、靜態重試）、BUILD 的步進與接觸設定。
- **提供**：「這個狀態是方程的正確解」的保證，以及誤差上界。
- **需要**：[速度] 給它做收斂研究的機器時間（0.1 mm cage 的記憶體需求，見 NUM-01）。

### 2.3 [速度] 模擬速度
- **問題**：同一個答案，用最少的機器時間、磁碟和人力得到？
- **面向**：
  - 機器時間：SPD-01 每設計時間；SPD-02 視窗均衡（診斷）
  - 儲存：SPD-03 每設計輸出量、SPD-04 磁碟守門
  - 無人值守：SPD-05 作業韌性、SPD-06 無人值守時數
  - 吞吐與重工：SPD-07 吞吐；SPD-08 重工率（診斷）
- **元件**：SPLIT、GPUDIRECT、OPS（h19 排程器、h23 看門狗、`resume_all.sh`）、PREFLIGHT、RETARGET（h28／h29）；
  資源：32 核 cgroup、GPU 1–4、128 GiB、/raid 個人配額。
- **提供**：吞吐量、無人值守的連續運轉。
- **需要**：[觀測] 告訴它哪些狀態和變數可以不輸出；[多元] 給它不會一直翻轉、重試的模型。

### 2.4 [觀測] 只觀測關注目標
- **問題**：量的是不是我們關心的量？量得對、齊全、可追溯、有分類嗎？
- **面向**：
  - 終點相關性：OBS-01 終點齊全
  - 評估狀態：OBS-02 目標力矩插值、OBS-03 無效狀態濾除、OBS-04 振幅達標不靠猜
  - 完整性：OBS-05 自動完整性檢查、OBS-06 彙整覆蓋率；OBS-11 靜默錯誤延遲（診斷，屬結果指標）
  - 指標正確性：OBS-07 指標程式自測
  - 可追溯：OBS-08 h24 起跑前一致性；OBS-09 完整來源（診斷）
  - 分類：OBS-10 非 pass 都有標籤
- **元件**：BUILD 的 Output 區段、METRICS（e03 mu_req、e04 滑出、e05 壓縮；e06 提案）、COLLECT、PREFLIGHT、XPLT。
- **提供**：每個設計的 pass／fail／open 與其依據，以及每個數字的來源。
- **需要**：[物理]、[數值] 提供有意義且正確的狀態；[速度] 不要為了快而刪掉它需要的狀態（OBS-02 需要包夾目標的兩個狀態）。

### 2.5 [多元] 容納多元設計
- **問題**：各種設計都能被表示、算到判定，而且不靠均質化或設計專屬調參？
- **面向**：
  - 表示：DIV-01 設計空間可表示；DIV-06 取樣多樣性（診斷）
  - 細節保真：DIV-02 不均質化（PI 2026-10-31 規則）
  - 可計算率：DIV-03
  - 程序普適：DIV-04 失敗無偏；DIV-05 無設計專屬調參（診斷）
- **元件**：MESH（h12：家族 A／B、gradient、fabrication、d；evo 0.2 mm 體素場）、EQLAW（h32，只換最外層 0.2 mm）、AL。
- **提供**：任何設計都能走完「建模 → 插入 → 負荷 → 六視窗」而得到明確判定。
- **需要**：[數值] 一個對軟薄層穩健的接觸與求解；[速度] 容忍較小的步長或重試。

### 2.6 [泛化] 結論穩健性　次要，暫緩
- **問題**：判定在合理的不確定範圍內會不會翻轉？
- **登錄的檢查**：GEN-01 解剖變異（59／64 歲）、GEN-02 材料離散、GEN-03 摩擦係數 0.2／0.45、GEN-04 手術置入偏差、GEN-05 規則門檻敏感度。
  指標統一用「判定翻轉率」。
- **暫緩期間的義務**：每份結論附上 R07 範圍聲明。

### 2.7 [時程] 支撐期覆蓋　次要，暫緩
- **問題**：BIOCAGE 要在 biodisc 成熟期間（≥ 16 週）提供支撐。平台能不能回答 0 到 16 週以上的問題，而不只是 t = 0 的快照？
- **登錄的檢查**：TIM-01 軟相降解（敏感度已跑）、TIM-02 硬相蠕變破裂、TIM-03 壓縮永久變形、TIM-04 biodisc 成熟後的負荷分擔、TIM-05 疲勞（PI 已決定延後）。
- **暫緩期間的義務**：每份結論附上 R08 範圍聲明。

### 非能力標籤
- **[設計]**：平台完成了它的工作，設計該被淘汰
- **[決定]**：判定規則或門檻還沒定，由 PI 決定
- **[流程]**：治理、文件、版本控制

## 3. 事件分類：一個 run 出問題，先標誰

依序問，第一個成立的就是主標籤（可以加副標籤）。標籤寫法 `[能力]/<面向>`，例如 `[數值]/temporal`、`[多元]/computability`、
`DESIGN/compression-lowerbound`、`DECISION/compression-limits`。這個標籤寫進 DECISIONS、工作名稱註記，以及 collect_split 的
`class` 欄位（OBS-10）。

| # | 觀察到的現象 | 主標籤／面向 | 下一步 |
|---|---|---|---|
| 1 | 磁碟滿、OOM、程序被殺、排程停擺、job 消失 | [速度]/unattended | 修作業層，重排 run（結果不算） |
| 2 | 結果檔缺、視窗少、exit code 與結束行不一致、旋轉沒施加 | [觀測]/integrity | 完整性報告（OBS-05） |
| 3 | 末步 dt < 1e-4，或力矩、位移在末步跳變 > 2×，或該態的剛體動態殘差 |M_rb| > 2% 目標（重試步） | [數值]/temporal；被判定採用時加 [觀測]/state | 該態永不使用（e03.filter_rows 自動）；有丟棄且未在有效態結束 → [數值]/unstable-window |
| 4 | 翻轉或不收斂發生在**骨**（C3／C4 皮質骨、小面關節區） | [數值]/contact | 步長、罰則、網格；不得歸咎設計 |
| 5 | 同一設計在另一種求解模式（靜態／動態／配置）算得完 | [數值]/approximation | 以 NUM-08／NUM-09 比對兩種結果；記錄採用哪一種 |
| 6 | 插入階段（t < 3）停，翻轉在 cage，軟層壓縮 < 15% | [多元]/computability | h32 等效律或插入參數；仍不行再問 PI 是否為「不可插入」設計 |
| 7 | 跟隨負荷階段（t 3–3.5）停，翻轉在 cage 軟層，最後狀態軟層壓縮 > 15% | [設計]（附「平台未算完」註記） | 標 `DESIGN/compression-lowerbound` |
| 8 | 同 7，但壓縮 < 15% | [多元]/computability | 同 6 |
| 9 | 視窗正常結束，但反力矩沒到 1.5 N·m | [觀測]/state | 重定振幅再跑（OBS-04）；永遠不以此淘汰設計（R02） |
| 10 | 算得穩定、數值檢查都過，但與實驗或文獻不符 | [物理]/<面向> | 對照實驗、修模型（記入 DECISIONS） |
| 11 | 六個視窗都達標，規則判定 fail（壓縮）或 mu_req 太高 | [設計] | 淘汰；記錄是哪條規則 |
| 12 | 判定依賴的規則尚未確定（壓縮上限、135 N、不可計算案例） | [決定] | 列入 PI 決定清單 |

## 4. 變更流程：改一個元件之前

1. `python scripts/8_audit/h33_capability_audit.py impact <元件 ID 或檔案路徑>`，列出所有依賴它的檢查與受影響的能力。
2. 填影響評估，寫進 DECISIONS 的日期條目：

```
標的能力：[  ]/<面向>      修法：
改動的元件：              impact 列出的必要檢查：
對 [物理] [數值] [速度] [觀測] [多元] 各自的影響（+／−／0／?）：
要重跑的檢查（必要的全部；診斷的擇要）：
會改變哪些既有判定（pass/fail/open 名單）：
```

3. 改完後重跑檢查，更新 json 的 status，再跑 h33 重新產生計分表。只改到無關內容（例如路徑字串）時，登錄 `reconfirmed`。

## 4a. 評估狀態與完整性的常規（2026-11-02）

- **判定狀態**：e03 `target_bracket` 取包夾 1.5 N·m 的兩個有效狀態線性插值（取代「跨過目標的第一步」）；e04 在兩態各算一次再插值，e05 取包夾下態之前的最大值與插值之大者。
- **無效狀態**（`e03.filter_rows`，判定永不使用）：dt < 1e-4 的微步（FEBio must-point／步末控制器的設計行為，慢速動態下產生偽慣性力矩）；**剛體動態殘差**（C3pot.txt 的 |M_rb| > 2%×目標 = 30 N·mm；重試步、視窗起步、接觸顫動時被驅動剛體的慣性殘差，關節力矩少／多同樣的量；NUM-14，2026-11-02 晚）；孤立尖峰（與鄰點預測差 > max(0.15×目標, 1×預測)）；首列 > 3×目標。力殘差只記錄（`rb_fres_max`）不判定。h28 重定振幅、h31 `window_check`、h34 掃描用同一規則。
- **完整性**：h31 每視窗寫 `window_check.json`、每案例寫 `split_check.json`；舊批次用 `scripts/8_audit/h34_window_scan.py` 回溯（輸出 `WINDOW_SCAN_<date>.md`：微步／尖峰、翻轉元素所屬區塊、不可計算設計的分布）；collect_split 拒收沒有有效狀態的視窗，並為每個設計寫 `class`／`reason`。
- **每批結束**：跑 h34 → collect_split → h33；三者的輸出就是 NUM-04、NUM-06、OBS-05、OBS-10、DIV-03、DIV-04 的證據。
